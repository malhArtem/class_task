## Часть 1. Как придумать идею, которая не позорна

### Почему "Todo list" и "Блог" — это провал?

Потому что:
- Это есть в каждом втором проекте на GitHub.
- Там нет сложной бизнес-логики (всё сводится к CRUD — Create, Read, Update, Delete).
- Преподаватель видел это 500 раз.
- Вам нечего будет рассказывать на защите, кроме "я умею создавать таблицы".

Ваша цель — **решить проблему**, а не продемонстрировать знание синтаксиса.

---

### Правило №1: "Больно + Знакомо"

Задайте себе два вопроса:

1. **Где мне лично больно?** Что в моей жизни или жизни окружающих работает неудобно, медленно, дорого или глупо?
2. **В чём я разбираюсь?** Вы не можете сделать API для нейрохирургии, если вы филолог. Берите сферу, которую вы понимаете: хобби, учёба, спорт, работа, быт.

**Примеры из жизни студентов прошлых лет:**
- *"Я играю в D&D, и мастеру сложно отслеживать здоровье монстров"* → API для управления боями.
- *"В моём вузе расписание висит на доске, а я хочу получать уведомления об изменениях"* → API-парсер расписания.
- *"Моя девушка печёт торты на заказ, и она путается в заявках в WhatsApp"* → API для приёма заказов кондитера.
- *"Мы в офисе постоянно не можем найти свободную переговорку"* → API бронирования.

---

### Правило №2: "Убей 80% функций"

Вы делаете не продукт на год, а **проект на 2-3 недели**. Поэтому:

1. Возьмите самую большую проблему.
2. Отрежьте от неё всё, кроме самого важного.
3. То, что осталось — это ваш MVP (Minimum Viable Product — минимально жизнеспособный продукт).

**Плохо:** "Сделаю Uber для доставки еды с трекингом курьера в реальном времени, чатом и системой скидок".  
**Хорошо:** "Сделаю API, где ресторан выкладывает меню, а клиент может оформить заказ и посмотреть его статус (без геолокации, без чата)".

---

### Метод "Скажи нет трендам"

Не берите:
- Криптовалюты / блокчейн
- Искусственный интеллект (если вы не знаете матчасть)
- Маркетплейсы с тысячами товаров
- Социальные сети с лентой новостей

Берите **узкую нишу**:
- Бронирование столиков в антикафе
- Учёт личных расходов с категориями (не умный ИИ-банкинг)
- Система голосования за проекты в классе
- Доска объявлений для студентов с поиском по предметам

---

### Практическое задание №1 (выполните прямо сейчас)

Выпишите на лист бумаги три колонки:

| Что меня бесит / неудобно | В чём я разбираюсь | Упрощённая идея (убрав 80%) |
|---------------------------|-------------------|----------------------------|
|                           |                   |                            |
|                           |                   |                            |
|                           |                   |                            |

**Пример заполнения:**
| Что бесит | В чём разбираюсь | Идея для проекта |
|-----------|------------------|------------------|
| Теряю заметки с рецептами | Люблю готовить | API для хранения рецептов с поиском по ингредиентам |
| Сложно собирать деньги на подарок коллеге | Работаю в команде | API для "складчины" (общий котёл с учётом взносов) |

**Выберите одну идею из третьей колонки** и переходите к Части 2.

## Часть 2. Как сформулировать бизнес-требования (BRD)

BRD — это документ на **человеческом языке**. Его должен понять не только программист, но и заказчик (даже если заказчик — это ваш сосед по парте).

### Структура BRD (заполните все пункты)

---

#### 1. Название проекта

**Правило:** Название должно быть говорящим.  
**Плохо:** "MyProject"  
**Хорошо:** "BookDesk" (бронирование столов), "ReceiptKeeper" (хранитель рецептов), "SplitWiseLite" (лёгкая версия разделения счетов).

**Ваш вариант:** ____________________

---

#### 2. Целевая аудитория

Опишите портрет пользователя. Не "все люди", а конкретно.

**Шаблон:**
- Кто это? (студент, офисный работник, домохозяйка, владелец малого бизнеса)
- Сколько им лет?
- Какой у них уровень технической грамотности?
- Какую проблему они решают с вашим сервисом?

**Пример:**
> *Целевая аудитория — сотрудники IT-компании от 25 до 40 лет. Они технически подкованы, но не хотят тратить время на хождение по этажам в поисках свободной переговорки. Им нужен быстрый доступ с телефона.*

**Ваш вариант:** ____________________

---

#### 3. Бизнес-цель (одна, главная)

Сформулируйте **одну измеримую цель**. Используйте конструкцию "Сократить / Увеличить / Упростить".

**Шаблон:**  
"Сервис помогает [кому?] [что сделать?], чтобы [какой результат получить?]"

**Плохо:** "Сделать удобное приложение" (неизмеримо)  
**Хорошо:** "Сервис помогает сотрудникам бронировать переговорки за 30 секунд, чтобы сократить время на организацию встреч с 15 минут до 2 минут".

**Ваш вариант:** ____________________

---

#### 4. Роли пользователей

Опишите, кто есть в системе. Минимум 2 роли. Одна из них обязательно **администратор** (у него есть права, которых нет у других).

**Шаблон:**
- **Гость (неавторизованный):** может только смотреть ограниченный набор данных.
- **Пользователь:** зарегистрированный юзер, может создавать и редактировать СВОИ объекты.
- **Модератор/Админ:** может управлять ВСЕМИ объектами, блокировать пользователей и т.д.

**Пример:**
> 1. **Пользователь:** регистрируется, создаёт рецепты, редактирует только свои, ставит оценки чужим.  
> 2. **Админ:** может удалять или редактировать ЛЮБЫЕ рецепты, блокировать пользователей-нарушителей.

**Ваш вариант:**
- Роль 1: ____________________ (что может?)
- Роль 2: ____________________ (что может?)
- Роль 3 (если есть): ____________________

---

#### 5. Функциональные требования (Must Have)

Это список того, что система **обязана** уметь делать. Без этого проект бессмысленен.

**Правило:** Описывайте с точки зрения пользователя, используя глаголы.

**Плохо:** "Реализовать CRUD для пользователей"  
**Хорошо:** "Пользователь может зарегистрироваться по email и паролю"  
**Хорошо:** "Администратор может просматривать список всех зарегистрированных пользователей"

**Разбейте на группы:**

**Аутентификация и профиль:**
- [ ] Пользователь может зарегистрироваться
- [ ] Пользователь может войти в систему
- [ ] Пользователь может изменить свой пароль
- [ ] Пользователь может посмотреть свой профиль

**Основной функционал:** (замените на свой)
- [ ] Пользователь может создать новый рецепт
- [ ] Пользователь может посмотреть список всех рецептов
- [ ] Пользователь может посмотреть детали одного рецепта
- [ ] Пользователь может отредактировать СВОЙ рецепт
- [ ] Пользователь может удалить СВОЙ рецепт
- [ ] Пользователь может поставить оценку чужому рецепту

**Администрирование:**
- [ ] Админ может удалить ЛЮБОЙ рецепт
- [ ] Админ может заблокировать пользователя

**Ваш список (перенесите в этот блок):**  
___________________________________
___________________________________
___________________________________

---

#### 6. Бизнес-правила (самое важное!)

Это **неочевидная логика**, которую нужно запрограммировать. Здесь обычно происходят ошибки, потому что студенты про них забывают.

**Заполните по шаблону "Если ... то ...":**

| Условие | Что должно произойти |
|---------|----------------------|
| Если пользователь пытается удалить чужой рецепт | Система возвращает ошибку 403 Forbidden |
| Если пользователь ставит оценку 5 рецепту | Средний рейтинг рецепта пересчитывается |
| Если пользователь пытается забронировать уже занятый стол | Система возвращает ошибку "Место занято" |
| Если пользователь не подтвердил email | Он не может создавать рецепты |
| Если пользователь ввёл неверный пароль 5 раз подряд | Аккаунт блокируется на 15 минут |

**Ваши бизнес-правила:**
1. Если ________________________________, то ________________________________.
2. Если ________________________________, то ________________________________.
3. Если ________________________________, то ________________________________.
4. Если ________________________________, то ________________________________.

---

#### 7. НЕ-требования (что мы НЕ делаем)

Это защита от "золотых" ожиданий. Напишите, что сознательно выносите за рамки проекта. Это покажет, что вы понимаете границы MVP.

**Пример:**
> - Мы НЕ делаем мобильное приложение (только REST API).
> - Мы НЕ реализуем восстановление пароля через email.
> - Мы НЕ поддерживаем загрузку изображений.
> - Мы НЕ делаем историю изменений рецепта.

**Ваш список НЕ-требований:**
- Мы НЕ делаем ________________________________
- Мы НЕ делаем ________________________________
- Мы НЕ делаем ________________________________

## Итоговый чек-лист: ваш BRD готов, если...

Перед тем как сдать мне (преподавателю) ваш документ, проверьте себя:

- [ ] Название проекта есть и оно понятное.
- [ ] Описана конкретная целевая аудитория (не "все").
- [ ] Сформулирована одна измеримая бизнес-цель.
- [ ] Выделено минимум 2 роли (Пользователь + Админ).
- [ ] Функциональные требования разбиты по группам и написаны глаголами.
- [ ] Есть минимум 3 бизнес-правила (логика, которую нужно запрограммировать).
- [ ] Есть список того, что мы сознательно НЕ делаем.
- [ ] Весь текст написан на человеческом языке, понятном не-программисту.

## Пример готового BRD (для ориентира)

**Проект:** "ClassVote" — система голосования за студенческие проекты.

**Целевая аудитория:** Студенты и преподаватели вуза. Преподаватели выставляют проекты на голосование, студенты голосуют за понравившиеся.

**Бизнес-цель:** Сократить время сбора голосов с 3 дней до 15 минут и автоматически подсчитать победителя.

**Роли:**
- **Студент:** может просматривать проекты и голосовать (1 голос на проект).
- **Преподаватель:** может создавать, редактировать, удалять ЛЮБЫЕ проекты, видеть статистику голосов.
- **Админ:** может управлять пользователями (блокировать/разблокировать).

**Функциональные требования:**
- Студент может зарегистрироваться и войти.
- Преподаватель может создать проект (название, описание, категория).
- Студент может проголосовать за проект (только один раз за проект).
- Преподаватель может видеть рейтинг проектов.
- Админ может заблокировать студента, чтобы он не голосовал.

**Бизнес-правила:**
1. Если студент уже голосовал за проект, повторный голос отклоняется с ошибкой.
2. Если студент заблокирован, он не может голосовать ни за один проект.
3. Если проект удалён, все голоса за него автоматически аннулируются.
4. Преподаватель не может удалить проект, если за него проголосовало больше 10 студентов.

**НЕ-требования:**
- Мы НЕ делаем личные сообщения между студентами.
- Мы НЕ делаем загрузку файлов к проекту.
- Мы НЕ делаем экспорт в Excel (только JSON).

## Что делать дальше?

1. **Заполните все шаблоны выше** в отдельном документе (Google Docs / Word).
2. **Пришлите мне в дз** ваш BRD на проверку.
3. **Я напишу комментарии или обсудим на паре** — где логика хромает или где слишком сложно.
