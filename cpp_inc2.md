# Инкапсуляция в C++ — занятие для новичков (улучшенная версия)

## 🏦 Сначала — зачем это всё

Представь банкомат. Ты не можешь открыть корпус и покрутить колёсики, чтобы изменить свой баланс. Ты можешь только нажимать **кнопки**: «снять», «положить», «проверить баланс». Если денег мало — банкомат скажет «недостаточно средств».

Класс в C++ — это такой же банкомат:
- **внутренности** (данные) спрятаны — это `private`;
- **кнопки** (публичные методы) — это `public`;
- если данные плохие — метод **откажет**.

Это и есть **инкапсуляция**: *данные спрятаны, доступ — через методы*.

> 💡 Небольшое отступление про исключения. В заданиях мы будем писать `throw std::invalid_argument("...")` — это способ сказать «так нельзя». Его нельзя проигнорировать, как случайно возвращённый `false`. Если не перехватить — программа остановится с сообщением.
> ```cpp
> #include <stdexcept>
> if (v < 0) throw std::invalid_argument("value must be >= 0");
> ```

# Шаг 1. Приватные поля + публичные методы

## Теория

| Уровень | Кто видит |
|---|---|
| `private` | только методы **этого же** класса |
| `public` | все, включая `main` |

Два инструмента доступа к данным:

- **Геттер** — читает поле: `int get() const { return value_; }`
- **Сеттер** — пишет с **проверкой**:
  ```cpp
  void set(int v) {
      if (v < 0) throw std::invalid_argument("negative");
      value_ = v;
  }
  ```



> ⚠️ Почему `const` у геттера? Если объект объявлен `const`, у него можно вызывать только `const`-методы. Без `const` геттер «не увидит» `const`-объект.

**Зачем это нужно** — две причины:
1. Нельзя испортить данные снаружи (`acc.balance = -1000;` — не скомпилируется).
2. Метод **проверяет** значение перед записью.

# Шаг 2. Когда сеттер не нужен и когда он вреден

## Теория

Не на каждое поле нужен сеттер — это не «правило на автомате».

**Случай 1. Read-only поле.** Значение задаётся один раз в конструкторе и больше не меняется. Сеттера нет — есть только геттер.

```cpp
class User {
private:
    std::string email_;          // не меняется после создания
public:
    User(std::string e) : email_(e) {}
    std::string getEmail() const { return email_; }
    // сеттера нет!
};
```
Примеры: email, номер паспорта, дата рождения.

**Случай 2. Связанные поля.** Два поля должны меняться *вместе*. Если дать по сеттеру на каждое — можно получить невозможное состояние.

```cpp
// Плохо: можно получить «выключенный свет яркостью 200» или «яркость -5»
void setOn(bool v);
void setBrightness(int b);

// Хорошо: операции, которые держат состояние согласованным
void turnOn();
void turnOff();
void dim(int percent);   // меняет яркость, но только в [0..100]
```

**Правило:** если два поля связаны — **не давай менять их по отдельности**.

# Шаг 3. Вычисляемые поля — не хранить, а считать

## Теория

Если значение **можно вычислить** из других полей — его **не надо хранить**. Иначе забудешь пересчитать после изменения, и данные разойдутся.

Плохо:
```cpp
class Rectangle {
private:
    int width_  = 1;
    int height_ = 1;
    int area_   = 1;              // дублирование!
public:
    void setWidth(int w) { width_ = w; /* area_ забыли! */ }
    int  getArea() const { return area_; }
};
```
Если поставить `width = 5`, `getArea()` всё равно вернёт `1` — **баг**.

Хорошо:
```cpp
class Rectangle {
private:
    int width_  = 1;
    int height_ = 1;
public:
    void setWidth(int w)  { width_ = w; }
    void setHeight(int h) { height_ = h; }
    int  area() const { return width_ * height_; }   // всегда актуально
};
```

**Правило:** храни только **исходные** данные. Остальное — считай.

# Шаг 4. Не отдавай внутренности наружу

## Теория

Если геттер возвращает **неконстантную ссылку** на приватное поле — инкапсуляция ломается: через ссылку поле можно менять.

**Простейший пример — с `int`:**
```cpp
class Wallet {
private:
    int balance_ = 0;
public:
    int& getBalance() { return balance_; }   // ОПАСНО
};
// Пользователь:
w.getBalance() = -500;   // скомпилируется и обойдёт всю защиту
```

`int&` — это **псевдоним** переменной. Через него можно писать так же, как в поле.

**То же самое с контейнером `std::vector`** (динамический массив из STL):
```cpp
std::vector<std::string>& getSongs() { return songs_; }
// пользователь: playlist.getSongs().clear();  — обошёл всё
```

**Три способа починить (от простого к строгому):**

1. **`const`-ссылка** — читать можно, менять нельзя:
   ```cpp
   const std::vector<std::string>& getSongs() const { return songs_; }
   ```
2. **Возвращать копию** — безопасно, но дороже:
   ```cpp
   std::vector<std::string> getSongs() const { return songs_; }
   ```
3. **Вообще не отдавать контейнер**, а дать операции:
   ```cpp
   int size() const;
   std::string songAt(int i) const;
   void addSong(const std::string& s);
   ```

**Правило для новичка:** если геттер возвращает **ссылку или указатель** — подумай дважды.

# Шаг 5. Конструктор и инвариант

## Теория

**Инвариант** — правило, которое должно быть истинно **всегда**, пока объект существует. Примеры:
- «возраст в `[0, 150]`»;
- «знаменатель ≠ 0»;
- «обе стороны прямоугольника > 0».

Защищать инвариант нужно в **двух местах**:

1. **В конструкторе** — иначе можно создать объект, который сразу неправильный.
2. **В сеттере** — иначе можно испортить его позже.

```cpp
class Age {
private:
    int age_;
public:
    explicit Age(int a) {
        if (a < 0 || a > 150) throw std::invalid_argument("bad age");
        age_ = a;
    }
    int get() const { return age_; }

    void set(int a) {
        if (a < 0 || a > 150) throw std::invalid_argument("bad age");
        age_ = a;
    }
};
```

> 💡 `explicit` перед конструктором с одним аргументом запрещает случайное `Age a = 30;` — только `Age a(30);`. Мелочь, но помогает не писать код по ошибке. Пока можешь просто запомнить.

**Почему исключение, а не «тихо поправить»?** Если молча исправить `-5` на `0`, вызывающий код решит, что всё хорошо, и поедет дальше с неправильными данными. Исключение сразу сообщает: «ты сделал что-то не то».

# 🎯 Сводка: правила для новичка

1. **Поля — `private`.** Доступ — через методы.
2. **Геттер читает, сеттер пишет + проверяет.** Геттер помечаем `const`.
3. **Read-only поле** = геттер есть, сеттера нет.
4. **Связанные поля** = одна операция вместо двух сеттеров.
5. **Вычисляемое** = метод, а не поле (`area()`, `average()`).
6. **Не возвращай ссылку или указатель** на приватное поле без серьёзной причины.
7. **Инвариант защищаем в конструкторе И в сеттерах.** Ошибка — исключение, а не тихая правка.
