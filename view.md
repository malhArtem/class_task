## Краткая теория

`VIEW` — это именованный сохранённый запрос `SELECT`. Данные в нём не хранятся: каждый раз при обращении к `VIEW` SQLite заново выполняет внутренний запрос. `VIEW` используется для:

1. **Скрытия сложности** — длинный запрос с несколькими `JOIN` превращается в короткий `SELECT * FROM view`.
2. **Фиксации бизнес-правила в одном месте** — формула или фильтр описаны один раз, а не дублируются в каждом отчёте.
3. **Узкого интерфейса** — приложение видит только разрешённые столбцы.
4. **Стабильного контракта** — схема таблиц может меняться, а интерфейс `VIEW` остаётся прежним.

**Ограничение SQLite:** `VIEW` по умолчанию доступен только для чтения. `INSERT`, `UPDATE`, `DELETE` через `VIEW` невозможны.

## Пример: как создать первое VIEW

Разберём на простом примере, как `VIEW` создаётся, проверяется и изменяется. Этот пример **не входит в задания** — он только демонстрирует механику.

### Шаг 1. Сначала — обычный SELECT

Допустим, нам нужен список дорогих товаров (дороже 1000) — только название и цена:

```sql
SELECT name, price
FROM products
WHERE price > 1000;
```

Результат:

| name | price |
|---|---|
| Ноутбук | 70000 |
| Мышь | 1500 |
| Книга по SQL | 2000 |

### Шаг 2. Оборачиваем в VIEW

Добавляем `CREATE VIEW имя AS` перед запросом:

```sql
-- Назначение: товары дороже 1000
-- author: Иванов
CREATE VIEW v_expensive_products AS
SELECT name, price
FROM products
WHERE price > 1000;
```

Ничего не выполнилось — SQLite только **сохранил текст запроса** под именем `v_expensive_products`. Данные не хранятся, `VIEW` — это именованный запрос.

### Шаг 3. Проверяем

```sql
SELECT * FROM v_expensive_products;
```

Результат — тот же, что был в шаге 1. Если нужна другая сортировка — `ORDER BY` добавляется **снаружи** `VIEW`:

```sql
SELECT * FROM v_expensive_products ORDER BY price DESC;
```

Поэтому `ORDER BY` обычно не включают в определение `VIEW` — иначе `VIEW` жёстко фиксирует сортировку, и переиспользовать его с другим порядком не получится.

### Шаг 4. Смотрим, что сохранилось

```sql
.schema v_expensive_products
```

Вывод:

```sql
CREATE VIEW v_expensive_products AS
SELECT name, price
FROM products
WHERE price > 1000;
```

Это и есть `VIEW`: SQLite хранит текст запроса в системной таблице `sqlite_master`.

### Шаг 5. Изменяем VIEW

Если нужно поменять логику — `VIEW` **пересоздают**. Просто `CREATE` второй раз не сработает: SQLite выдаст ошибку `table v_expensive_products already exists`. Сначала удаляем:

```sql
DROP VIEW v_expensive_products;
```

Потом создаём заново с новым условием (например, дороже 2000):

```sql
-- Назначение: товары дороже 2000
-- author: Иванов
CREATE VIEW v_expensive_products AS
SELECT name, price
FROM products
WHERE price > 2000;
```

Проверяем: `SELECT * FROM v_expensive_products;` — теперь только «Ноутбук». «Книга по SQL» стоит ровно 2000 и не проходит по `> 2000`.

### Шаг 6. Удаляем, если не нужно

```sql
DROP VIEW v_expensive_products;
```

`VIEW` удалён, а таблица `products` и её данные остались на месте — `VIEW` их не трогает.

### Что важно запомнить из примера

| Действие | Синтаксис |
|---|---|
| Создать | `CREATE VIEW имя AS SELECT ...;` |
| Проверить | `SELECT * FROM имя;` |
| Посмотреть определение | `.schema имя` |
| Изменить | `DROP VIEW имя;` + `CREATE VIEW имя AS ...;` |
| Удалить | `DROP VIEW имя;` |

- `CREATE VIEW имя AS SELECT ...` — единственный новый синтаксис по сравнению с обычным `SELECT`.
- `VIEW` **не хранит данные** — только текст запроса.
- `ORDER BY` обычно выносят за пределы `VIEW` — так его можно переиспользовать с разной сортировкой.
- Чтобы изменить `VIEW`, его **удаляют и создают заново**. Просто повторный `CREATE` выдаст ошибку.
- `DROP VIEW` **не удаляет** базовые таблицы и их данные.

Теперь переходите к заданиям — там тот же механизм, только `SELECT` внутри `VIEW` сложнее.

### Задание 1. Детали оплаченных заказов

**Ситуация.** Аналитик каждое утро смотрит детали оплаченных заказов, копируя длинный запрос из текстового файла. В запросе три `JOIN` и фильтр `WHERE status = 'paid'`. Копируя руками, он может случайно удалить фильтр — и отчёт молча включит отменённые заказы.

**Задача.** Создайте представление `v_order_details`, которое возвращает `order_id, order_date, customer_name, product_name, quantity, unit_price, line_total` (`line_total = quantity * unit_price`) только для оплаченных заказов.

В вашей команде принято подписывать код: в комментарии перед `CREATE VIEW` укажите автора в формате `-- author: <ваша фамилия>`.

**Что должно получиться:**

| 1 | 2026-01-15 | Анна | Мышь | 2 | 1500 | 3000 |
| 2 | 2026-02-10 | Анна | Книга по SQL | 1 | 2000 | 2000 |

**Шаги:**

3. Проверьте: `SELECT * FROM v_order_details ORDER BY order_id, product_name;` — результат должен совпасть с таблицей.

**Зачем это нужно.** `VIEW` убирает целый класс ошибок: фильтр `status = 'paid'` невозможно случайно удалить, потому что в отчёте его нет — он внутри `VIEW`.

### Задание 6. Ограничения: VIEW — не таблица
