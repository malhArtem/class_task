# Полиморфизм

## Блок 1. В чём проблема

Есть три **разных** класса:

```cpp
class Email { public: void send() { std::cout << "Email отправлен\n"; } };
class Sms   { public: void send() { std::cout << "Sms отправлено\n"; } };
class Push  { public: void send() { std::cout << "Push отправлен\n"; } };
```

Ты хочешь в `main` положить их в **один вектор** и вызвать `send()` у всех **одним циклом**:

```cpp
std::vector<???> all;
// Что тут писать? Email? Sms? Push? — они же РАЗНЫЕ типы.
```

Почему так нельзя? Потому что `std::vector<T>` — это «массив **однотипных** элементов». Компилятор должен знать **размер** одного элемента и **как его копировать**. У `Email`, `Sms` и `Push` разные размеры и разные правила копирования — положить их в один `vector` невозможно.

**Что делать?** Нужен способ сказать: «это всё — **одно и то же с точки зрения обработки** (у всех есть `send()`), но ведут они себя по-разному». Именно это и даёт полиморфизм.

**Полиморфизм** позволяет:
1. Положить объекты разных классов в **один контейнер** — но **не сами объекты**, а **указатели** на них. Указатель — это всегда просто адрес (размер фиксирован), поэтому `std::vector<Animal*>` работает.
2. Вызвать **один и тот же метод** через указатель — а сработает **разная реализация** в зависимости от того, какой реально объект лежит по этому адресу.

## Блок 2. Общий родитель и указатель

**Первое:** нужен родитель, который говорит «у всех, кто меня наследует, есть `say()`».

**Второе:** указатель на родителя может смотреть на **любого** наследника — потому что «Cat **является** Animal». Это называется **восходящее преобразование** (upcast).

```cpp
// ─── РОДИТЕЛЬ ───
class Animal {
public:
    virtual void say() { std::cout << "какой-то звук\n"; }
    virtual ~Animal() { }
    // ↑ virtual — пока просто запомни: "разрешаю наследникам переопределить".
    //   Что именно это даёт — в блоке 3.
    //   virtual ~ — "при delete через Animal* удалится реальный объект".
    //   Почему это критично — в блоке 6.
};

// ─── НАСЛЕДНИКИ ───
class Cat : public Animal {
public:
    void say() override { std::cout << "Мяу\n"; }
    //           ↑ override = "проверь, что я правда переопределяю метод родителя".
    //             Если в родителе нет виртуального say() с такой сигнатурой —
    //             компилятор скажет.
};

class Dog : public Animal {
public:
    void say() override { std::cout << "Гав\n"; }
};

class Cow : public Animal {
public:
    void say() override { std::cout << "Му\n"; }
};
```

Теперь `Cat` является `Animal`, `Dog` является `Animal`, `Cow` является `Animal`. Значит:

```cpp
Cat c;
Animal* p = &c;   // ✅ указатель на Animal смотрит на Cat
                  //    "Cat является Animal" → это законно
                  //    c++ разрешает неявно: Cat* → Animal*

std::vector<Animal*> zoo;   // ← вот сюда теперь можно всех!
zoo.push_back(new Cat);
zoo.push_back(new Dog);
zoo.push_back(new Cow);
// Все элементы вектора — Animal*, размер фиксирован (8 байт на 64-bit).
// А за каждым указателем лежит РАЗНЫЙ объект.
```

**Важно понять:** `zoo[i]` — это **указатель**, а не объект. Объекты лежат где-то в куче (`new`), а вектор хранит только адреса. Именно поэтому «разнотипные» объекты помещаются в один контейнер — контейнер на самом деле однотипен (все элементы — `Animal*`).

## Блок 3. Что делает `virtual`

Пока у нас `say()` **виртуальный** — и всё работает: у каждого свой звук. Уберём `virtual` — и всё сломается:

```cpp
class Animal {
public:
    void say() { std::cout << "какой-то звук\n"; }   // ❌ БЕЗ virtual
};
```

Теперь тот же цикл напечатает **три раза** `"какой-то звук"`, а не «Мяу/Гав/Му». Почему?

**Без `virtual`** компилятор решает, **какую версию вызвать, ещё на этапе компиляции**, и смотрит при этом на **тип указателя** (`Animal*`). Он видит `Animal*` → берёт `Animal::say()`. Ему всё равно, что внутри реально лежит `Cat`. Это называется **статическое связывание** — решение «пришито» к коду на этапе компиляции.

**С `virtual`** решение принимается **в момент выполнения**, по **реальному** объекту за указателем. Внутри `Cat` → `Cat::say()`, внутри `Dog` → `Dog::say()`. Это **динамическое связывание**.

**Одной фразой:**
> `virtual` = «вызов через указатель/ссылку идёт по **реальному** объекту, а не по типу указателя».

**Почему это возможно технически?** У каждого объекта класса с виртуальными методами есть скрытый указатель на **таблицу виртуальных функций** (vtable). Там записано: «для класса `Cat` метод `say` — вот эта функция; для `Dog` — вот эта». При вызове `p->say()` программа:
1. Берёт объект по адресу `p`.
2. Смотрит его vtable.
3. Находит там `say` и вызывает.

Поэтому и получается «по реальному объекту». Именно поэтому `virtual` стоит небольших накладных расходов — один лишний переход по указателю. Незначительно, но знать полезно.

**Важно:** `virtual` достаточно объявить **один раз** — у родителя. Все наследники автоматически становятся «виртуальными» для этого метода. Писать `virtual` у каждого наследника не нужно (но `override` — нужно, это отдельное слово, см. блок 3.5).

## Блок 3.5. `override` — отдельное слово, не путать с `virtual`

Многие путают `virtual` и `override` — это **разные** вещи:

- **`virtual`** пишется **у родителя** и означает «разрешаю переопределить, вызов пойдёт по реальному типу».
- **`override`** пишется **у наследника** и означает «проверь, что я правда переопределяю существующий виртуальный метод».

`override` **не делает** метод виртуальным (он уже виртуальный, потому что виртуален в родителе). `override` — это **просьба к компилятору проверить**, что ты не опечатался.

**Зачем это нужно?** Представь, что ты опечатался:

```cpp
class Cat : public Animal {
public:
    void Say() override { std::cout << "Мяу\n"; }   // заглавная S
};
```

С `override` компилятор скажет: «в `Animal` нет виртуального метода `Say` — ты ничего не переопределяешь». Без `override` компилятор промолчит: он решит, что ты просто добавил **новый** метод `Say`, а старый `say` остался не переопределён. Программа скомпилируется, но при вызове через `Animal*` будет вызываться `Animal::say`, а не твой `Say`. Молчаливый баг.

**Правило:** **всегда** пиши `override` в наследниках. Всегда. Без исключений.

## Блок 4. Только через указатели и ссылки

Полиморфизм работает **только** через `*` или `&`. Через значение — ломается.

```cpp
void byValue(Animal a)      { a.say(); }   // ❌
void byRef(const Animal& a) { a.say(); }   // ✅
void byPtr(const Animal* a) { a->say(); }  // ✅

Cat c;
byValue(c);   // "какой-то звук" — срезка!
byRef(c);     // "Мяу"          — работает
byPtr(&c);    // "Мяу"          — работает
```

**Что произошло при `byValue(c)`?** Компилятор создал **новый объект типа `Animal`** и скопировал в него только родительскую часть `Cat`. Всё, что специфично для `Cat`, — **отрезалось**. Внутри функции лежит уже настоящий `Animal`, а не `Cat`. Это называется **срезка** (slicing).

**Почему так?** Потому что `byValue` принимает **значение** — компилятор должен создать локальную копию. А копия какого типа? Типа параметра — `Animal`. Он копирует только те байты, которые относятся к `Animal`, и «обрезает» всё, что добавил `Cat`.

**Запомни:** полиморфизм — про «смотреть на объект снаружи» (через указатель/ссылку). Скопировал по значению — обрезал до типа переменной.

**Ещё одна ловушка:** `std::vector<Animal>` (без звёздочки) — тоже **срезка**. Если положить туда `Cat`, он превратится в `Animal` при копировании. Внутри вектора будут «обрезки», а не коты. Поэтому в контейнерах для полиморфизма хранят **указатели** (`Animal*`) или **умные указатели** (`std::unique_ptr<Animal>`).

## Блок 5. Абстрактный класс

Часто у родителя **нет** осмысленной реализации. Какой звук у «просто животного»? Никакой. Звук есть только у **конкретных** животных.

Тогда метод делают **чисто виртуальным** — `= 0`:

```cpp
class Animal {
public:
    virtual void say() = 0;   // ← НЕТ реализации. Наследник ОБЯЗАН написать.
    virtual ~Animal() { }
};

// Animal a;        // ❌ нельзя создать объект
Animal* p = nullptr; // ✅ указатель можно
```

**Что даёт абстрактный класс:**
- **Нельзя создать объект** — `Animal a;` не скомпилируется. Это защита: «нельзя создать что-то, что не умеет делать то, что обязан».
- **Можно создать указатель/ссылку** — и смотреть через них на наследников.
- **Наследник обязан** переопределить все `= 0`-методы. Иначе он тоже абстрактный (и его тоже нельзя создать).

Это **контракт**: «любой, кто хочет называться Animal, обязан уметь издавать звук. Как именно — не моё дело».

**Зачем это нужно?** Абстрактный класс — это **интерфейс**. Он описывает «что должно быть», а не «как это делать». Ты пишешь код, который работает с любым `Animal*` — и знаешь наверняка, что у него есть `say()`. А конкретные реализации добавляются отдельно, не трогая код, который их использует. Это и есть **расширяемость**: добавил новый класс-наследник — старый код продолжает работать.

## Блок 6. Виртуальный деструктор

Раз мы храним наследников через `Animal*` и удаляем через `Animal*` — деструктор **обязан** быть виртуальным. Иначе при `delete` вызовется только `~Animal`, а деструктор реального объекта (`~Cat`) — **нет**. Всё, что `Cat` захватил, — утечёт.

```cpp
class Animal {
public:
    virtual void say() = 0;
    virtual ~Animal() { }   // ← обязательно, раз есть virtual-методы
};

class Cat : public Animal {
    int* data;   // что-то, что надо освободить
public:
    Cat() : data(new int[100]) { }
    ~Cat() override { delete[] data; }
    void say() override { std::cout << "Мяу\n"; }
};

int main() {
    Animal* p = new Cat;
    delete p;
    // с virtual ~: сначала ~Cat (освободит data), потом ~Animal ✅
    // без virtual:  только ~Animal → data утечёт ❌
}
```

**Почему так происходит?** `delete p` — это «вызови деструктор и освободи память». Какой деструктор? Если `~Animal` **не** виртуальный — компилятор смотрит на **тип указателя** (`Animal*`) и вызывает `Animal::~Animal`. Ему всё равно, что реально лежит `Cat`. С `virtual ~` — по тому же механизму vtable — вызовется `~Cat`, а потом `~Animal`.

**Правило на всю жизнь:**
> Есть хоть один `virtual`-метод → **деструктор делай `virtual`**.

Это правило легко запомнить по принципу: «если класс собирается участвовать в полиморфизме, он должен корректно удаляться через указатель на родителя».

## Шпаргалка

| Что | Зачем |
|---|---|
| `virtual` у метода родителя | «наследник может переопределить, вызов через указатель идёт по реальному типу» |
| `override` у наследника | «проверь, что я правда переопределяю» (не делает метод виртуальным!) |
| `= 0` у метода | «чисто виртуальный — наследник ОБЯЗАН реализовать» |
| `virtual ~` у родителя | «при `delete` через родительский указатель удалится реальный объект» |
| передача по значению | ❌ ломает полиморфизм (срезка) |
| `std::vector<Animal>` | ❌ срезка внутри контейнера |
| `std::vector<Animal*>` | ✅ полиморфизм работает |
