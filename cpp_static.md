# `this` и статические члены

## Блок 1. Проблема: метод не знает, с каким объектом работает

Начнём с вопроса, который обычно не задают, а зря. Вот класс:

```cpp
class Point {
public:
    int x, y;

    void moveRight() {
        x += 1;   // ← ЧЕЙ x здесь меняется?
    }
};

int main() {
    Point a{1, 2};
    Point b{10, 20};

    a.moveRight();
    b.moveRight();

    std::cout << a.x << " " << b.x << "\n";   // "2 11"
}
```

Стоп. `moveRight()` — это **одна и та же функция** в памяти. Она компилируется **один раз**. Но при вызове `a.moveRight()` она меняет `a.x`, а при `b.moveRight()` — `b.x`. **Как?!** Ведь внутри функции написано просто `x += 1;` — без указания, чей `x`.

Если бы ты писал это на чистом C, пришлось бы делать так:

```c
void point_moveRight(Point* self) {   // явно передаём указатель на объект
    self->x += 1;
}

point_moveRight(&a);
point_moveRight(&b);
```

То есть функция **обязана знать**, с каким объектом работает. В C это делают руками — передают указатель первым параметром.

**В C++ это делает компилятор — автоматически, незаметно.** И тот самый скрытый указатель, который он подставляет, называется `this`.

## Блок 2. Решение: `this` — скрытый указатель на объект

Внутри **любого нестатического метода** компилятор неявно подставляет указатель на объект, для которого метод вызван. Этот указатель называется `this`.

Что происходит «под капотом»:

```cpp
// Ты пишешь:
class Point {
public:
    int x, y;
    void moveRight() { x += 1; }
};

// Компилятор мысленно превращает это в:
class Point {
public:
    int x, y;
    void moveRight(Point* this) { this->x += 1; }   // ← this — скрытый параметр
};

// А вызов a.moveRight() — в:
Point_moveRight(&a);   // передаём адрес a
```

Отсюда всё сразу становится понятно:

- `a.moveRight()` → `this = &a` → меняется `a.x`
- `b.moveRight()` → `this = &b` → меняется `b.x`

**`this` — это:**
- **указатель** на объект (тип `Point*`, а не `Point`);
- **скрытый первый параметр** каждого нестатического метода;
- **автоматически** передаётся при вызове;
- **нельзя** присвоить (`this = ...;` — ошибка компиляции, потому что он константный: `Point* const this`).

**Ты можешь писать `this->x` явно** — результат тот же, что `x`. Обычно `this` явно нужен только в двух случаях:
1. **Параметр затеняет поле** (блок 4).
2. **Хочешь вернуть сам объект** (блок 3).

## Блок 3. Проблема: как построить цепочку вызовов?

Представь, что у класса много сеттеров:

```cpp
class Person {
public:
    std::string name;
    int age;
    std::string city;

    void setName(const std::string& n) { name = n; }
    void setAge(int a)                 { age = a; }
    void setCity(const std::string& c) { city = c; }
};

Person p;
p.setName("Аня");
p.setAge(25);
p.setCity("Москва");
```

Работает, но **три строки** на одно логическое действие — «настроить человека». Хочется короче:

```cpp
p.setName("Аня").setAge(25).setCity("Москва");
```

Чтобы это работало, каждый сеттер должен **вернуть что-то**, у чего есть следующий метод. То есть — **сам объект**. Но какой объект? Тот, для которого вызван метод — то есть `*this`.

## Блок 4. Решение: возвращать `*this` из методов

```cpp
class Person {
public:
    std::string name;
    int age;
    std::string city;

    Person& setName(const std::string& n) {
        name = n;
        return *this;   // ← вернуть САМ объект (по ссылке), чтобы продолжить цепочку
    }
    Person& setAge(int a) {
        age = a;
        return *this;
    }
    Person& setCity(const std::string& c) {
        city = c;
        return *this;
    }
};

Person p;
p.setName("Аня").setAge(25).setCity("Москва");   // ← одна строка, читается как фраза
```

Разберём по шагам, что происходит:

1. `p.setName("Аня")` — меняет `p.name`, возвращает `*this` — то есть **сам `p`** (по ссылке).
2. К результату применяется `.setAge(25)` — а результат — это `p`, значит меняется `p.age`.
3. К результату `.setAge(25)` — снова `p` — применяется `.setCity(...)`.
4. В итоге меняется всё у одного и того же `p`.

**Почему `*this`, а не `this`?**

- `this` — **указатель** (`Person*`). У указателя нет метода `setAge`.
- `*this` — **сам объект** (`Person`). К нему можно применять методы.

**Почему возвращаем `Person&`, а не `Person`?**

- Возврат `Person` (без `&`) — **копирует** объект. Тогда `p.setName("Аня")` изменит `p`, но вернёт **копию**. Следующий `.setAge(25)` изменит уже копию, а не `p`. Цепочка «сломается» — `p` получит только имя.
- Возврат `Person&` — возвращает **ссылку на тот же самый `p`**. Все вызовы работают с одним объектом.

**Почему нельзя вернуть ссылку на локальную переменную?**

```cpp
Person& bad() {
    Person local;
    return local;   // ❌ висячая ссылка: local умрёт после return
}
```

Ссылка на `*this` — безопасна, потому что `this` указывает на объект, который **живёт снаружи метода** (его создал вызывающий код). Он никуда не исчезнет по выходу из метода.

## Блок 5. Проблема: параметр называется так же, как поле

Классическая ситуация:

```cpp
class Point {
public:
    int x, y;

    void setX(int x) {
        x = x;   // ← ЧТО это делает?
    }
};

Point p;
p.setX(5);
std::cout << p.x;   // 0, а не 5 !!!
```

Почему `0`? Потому что компилятор при поиске имени `x` берёт **ближайшее** — это параметр `x`, а не поле. Значит `x = x;` — это «параметру присвоить значение параметра». Ничего не сломается, но и поле не изменится. **Молчаливый баг** — компилятор не ругается, программа работает неправильно.

Та же проблема была бы в конструкторе:

```cpp
Point(int x, int y) {
    x = x;   // ← оба x — параметры; поля остаются мусором
    y = y;
}
```

## Блок 6. Решение: `this->` явно указывает на поле

```cpp
class Point {
public:
    int x, y;

    void setX(int x) {
        this->x = x;
        // ↑ "полю объекта (this->x) присвоить значение параметра (x)"
    }
};
```

Теперь `this->x` однозначно означает **поле объекта**, а `x` справа — **параметр**. Никакой неоднозначности.

**Как ещё можно решить ту же проблему (стилистические варианты):**

1. **`this->`** — то, что мы только что сделали. Явно, но многословно.
2. **Переименовать параметр** — `void setX(int newX) { x = newX; }`. Самое частое решение: просто не создавать конфликт имён.
3. **Подчёркивание у полей** — `int x_, y_;` (или `int x_;` для поля и `int x` для параметра). Тоже популярно, особенно в стандартной библиотеке (`size_`, `data_` и т.п.).
4. **Список инициализации в конструкторе** — `Point(int x, int y) : x(x), y(y) {}`. Здесь `x(x)` — левый `x` — это поле, правый — параметр. Компилятор сам разбирается по позиции.

Выбери **один** стиль и придерживайся во всём проекте. Смешивать — плохо.

## Блок 7. Проблема: нужен счётчик, общий на все объекты

Ты пишешь класс `Counter` и хочешь узнать: **сколько объектов создано и живёт прямо сейчас**. Первая мысль — добавить поле:

```cpp
class Counter {
public:
    int total = 0;   // ← счётчик созданных
    int value = 0;

    Counter() { total++; }
};

Counter a, b, c;
std::cout << a.total;   // 1 — у a свой счётчик, он увеличился только при создании a
std::cout << b.total;   // 1 — у b свой, увеличился при создании b
std::cout << c.total;   // 1 — у c свой
```

Проблема: **у каждого объекта свой `total`**. Общего счётчика нет. Нам нужен **один `total` на весь класс**, чтобы каждый новый объект увеличивал **его же**.

**Второй пример той же проблемы:** в игре у тебя 1000 юнитов, и ты хочешь знать **общий** лимит ресурсов или **глобальный** номер хода. Это не свойство одного юнита — это свойство **всех** юнитов вместе.

## Блок 8. Решение: `static` поле — одно на класс

**Статическое поле** принадлежит **классу**, а не объекту. Оно **одно на всю программу** — сколько бы объектов ни было (хоть ноль), поле существует ровно в одном экземпляре.

```cpp
class Counter {
public:
    static int total;   // ← ОДНО на весь класс, не на каждый объект
    int value = 0;      // своё у каждого объекта

    Counter()  { total++; }   // увеличиваем ОБЩИЙ счётчик
    ~Counter() { total--; }
};

int Counter::total = 0;   // ← ОБЯЗАТЕЛЬНО определить снаружи
```

**Как это работает:**

- `int value;` — каждый объект `Counter` имеет **своё** поле `value`. У `a` одно, у `b` другое.
- `static int total;` — поле принадлежит **классу**. У `a`, у `b`, у `c` — **один и тот же** `total`. Меняешь через `a` — видно через `b`.

**Почему нужно определять снаружи (`int Counter::total = 0;`)?**

Внутри класса `static int total;` — это **объявление**: «такое поле есть, тип — `int`». Но **память под него ещё не выделена** — компилятор только записал в таблицу «класс `Counter` имеет статическое поле `int`».

Определение `int Counter::total = 0;` в `.cpp` — это **«вот здесь, по этому адресу, лежит `int` с начальным значением 0»**. Оно выделяет память.

Без определения: компилируется, но при **линковке** — ошибка `undefined reference to 'Counter::total'`. Линкер ищет «где же это поле», не находит.

**Современный вариант (C++17+):**

```cpp
class Counter {
public:
    inline static int total = 0;   // ← определение прямо в классе
    int value = 0;

    Counter()  { total++; }
    ~Counter() { total--; }
};
```

`inline` говорит: «это определение, но если встретится в нескольких `.cpp` — считай, что оно одно». Удобно для заголовочных файлов — не надо писать отдельную строку в `.cpp`.

**Где живёт статическое поле?** Не в объекте. Даже если объектов **ноль** — `Counter::total` существует и доступен. Это поле **класса**, а не экземпляра.

## Блок 9. Проблема: нужна функция, которая не работает с конкретным объектом

Есть класс `Math` — просто набор полезных математических операций:

```cpp
class Math {
public:
    double pi = 3.14159;   // ← зачем это поле в каждом объекте?
    double maxDegree = 360;

    double toRadians(double deg) { return deg * pi / 180.0; }
    //                              ↑ метод использует поле pi.
    //                                Но зачем создавать Math m; чтобы посчитать угол?
};
```

Проблема: `toRadians(90)` **не зависит от конкретного объекта** — она работает только с **переданным параметром** `deg` (и константой `pi`, которая одинакова у всех объектов). Заставлять пользователя создавать `Math m; m.toRadians(90);` — нелепо.

Второй пример: функция **фабрики** — «создать точку в начале координат». Ей тоже не нужен объект — наоборот, она **создаёт** объект.

Третий пример: функция **доступа к счётчику** — `getTotalAccounts()` — возвращает **общее** значение. Привязывать её к конкретному объекту бессмысленно.

**Общая проблема:** в классе нужны функции, которые **не работают с конкретным объектом** (`this` им не нужен). Обычный метод требует объект для вызова — это лишнее.

## Блок 10. Решение: `static` методы

**Статический метод** — метод, который **не привязан к объекту**. Его вызывают через `Класс::метод()` — без создания экземпляра.

```cpp
class Math {
public:
    static constexpr double PI = 3.14159265358979;   // константа класса

    static double toRadians(double deg) {            // статический метод
        return deg * PI / 180.0;
    }
};

// Вызов без объекта:
double r = Math::toRadians(90);
```

**Главное ограничение:** внутри статического метода **нет `this`**. Ведь для какого объекта? Ни для какого — метод вызван без объекта.

Следствие — **нельзя** обращаться к нестатическим полям и методам напрямую:

```cpp
class Counter {
public:
    inline static int total = 0;
    int value = 0;   // нестатическое

    static void reset() {
        total = 0;    // ✅ static — можно
        // value = 0; // ❌ ошибка: value нестатическое, this недоступен
    }
};
```

Почему? `Counter::reset()` вызывается **без объекта**. Компилятор не знает, **какой** `value` менять — их может быть 0, 1 или 1000. А `total` один на всех — его трогать безопасно.

**Зачем нужны статические методы — три сценария:**

### 1. Утилитарные функции

Логически принадлежат классу, но не работают с его объектами. Пример: `Math::toRadians`, `String::fromInt(42)`.

### 2. Фабрики — методы, создающие объекты

Классический пример — **фабричный метод**:

```cpp
class Point {
    int x, y;
    Point(int x, int y) : x(x), y(y) { }   // конструктор спрятан (private)

public:
    static Point origin()             { return Point(0, 0); }
    static Point fromPolar(double r, double a) {
        return Point(r * std::cos(a), r * std::sin(a));
    }
    void print() const { std::cout << x << " " << y << "\n"; }
};

Point p = Point::origin();                       // ✅ через фабрику
// Point q(1, 2);                                // ❌ конструктор приватный
```

Зачем прятать конструктор? Иногда хотят, чтобы объект создавался **только** через явные «фабрики» с понятными именами (`origin`, `fromPolar`), а не через случайный `Point(1, 2)`.

**Почему `origin()` может создать `Point`?** Потому что статический метод — **член класса**, он имеет доступ к приватным конструкторам.

### 3. Доступ к статическим полям через удобный интерфейс

```cpp
class Counter {
    inline static int total = 0;
public:
    static int getTotal() { return total; }   // читаемый интерфейс
};

int n = Counter::getTotal();
```

## Блок 11. Проблема: константы, принадлежащие классу

Класс `Math` содержит константу `PI`. Как её объявить?

- **`#define PI 3.14159`** — глобальный макрос, ни к какому классу не привязан, ломает пространства имён, плохо.
- **Глобальная переменная `double PI = 3.14;`** — одна копия, но глобальное имя — конфликтует с другими.
- **Обычное поле `double pi = 3.14;`** — копия **в каждом объекте**! У 1000 объектов — 1000 копий `pi`. Бессмысленная трата памяти.

Нужно: **константа класса, одна на всех, известная на этапе компиляции**.

---

## Блок 12. Решение: `static constexpr`

```cpp
class Math {
public:
    static constexpr double PI = 3.14159265358979;
    static constexpr int MAX_DEGREE = 360;

    static double toRadians(double deg) {
        return deg * PI / 180.0;
    }
};

// Использование:
double r = Math::toRadians(90);
double pi = Math::PI;                    // доступ к константе
int max = Math::MAX_DEGREE;
```

**Что даёт `static constexpr`:**

1. **Одна копия** на всю программу — не тратим память на каждый объект.
2. **`constexpr`** гарантирует, что значение известно **на этапе компиляции** — можно использовать в `switch`, размерах массивов, шаблонных аргументах и т.п.
3. **Принадлежит классу** — не засоряет глобальное пространство имён.
4. **Нельзя изменить** — `Math::PI = 3;` не скомпилируется.

**Разница `static const` vs `static constexpr`:**

- `static const` — константа, но **не обязательно** известна на этапе компиляции (может инициализироваться в рантайме).
- `static constexpr` — **гарантированно** известна на этапе компиляции. В современном C++ (C++11+) для констант **предпочитай `constexpr`**.

**Когда `constexpr`, а когда `const`?** Если значение можно вычислить на этапе компиляции — `constexpr`. Если оно зависит от чего-то, что становится известно только в рантайме (например, от аргументов командной строки) — `const`.

### ✏️ Упражнение 8. Класс `Account`

Создай класс «банковский счёт»:

**Статические члены:**
- `inline static int totalAccounts = 0;` — сколько счетов сейчас существует;
- `static constexpr double MIN_BALANCE = 0.0;` — минимальный баланс;
- `static int getTotalAccounts();` — статический метод.

**Обычные члены:**
- `std::string owner;`
- `double balance;`

**Конструктор:** `Account(const std::string& owner)` — увеличивает `totalAccounts`, ставит `balance = MIN_BALANCE`.

**Методы (нестатические):**
- `Account& deposit(double amount);` — прибавляет, возвращает `*this`;
- `Account& withdraw(double amount);` — вычитает, но не ниже `MIN_BALANCE`; возвращает `*this`;
- `void print() const;` — печатает `owner: balance`.

**Деструктор:** уменьшает `totalAccounts`.

В `main`:

```cpp
std::cout << Account::getTotalAccounts() << "\n";   // 0
{
    Account a("Аня");
    Account b("Боря");
    a.deposit(1000).withdraw(300).deposit(50);
    a.print();                                          // "Аня: 750"
    b.print();                                          // "Боря: 0"
    std::cout << Account::getTotalAccounts() << "\n";   // 2
}
std::cout << Account::getTotalAccounts() << "\n";       // 0
```

**Проверь:**
1. Цепочка `a.deposit(1000).withdraw(300).deposit(50)` работает. Если нет — посмотри, что возвращает каждый метод.
2. `withdraw` не уводит баланс ниже нуля.
3. `getTotalAccounts()` доступен без объекта.
